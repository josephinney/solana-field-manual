Two paths: consensus or applications

Once you understand the basics of Solana, there are two broad directions to go deeper. One is the layer that keeps the network running, and the other is the layer that people build on top of it. This article describes what each path involves, which skills it asks for and how to take a first step in each one.

  • levelbeginner
  • prerequisitesaccounts, transactions and validators
  • time~8 min
  • toolsSolana CLI, Node.js

01Two layers of the same network

Everything that happens on Solana involves two layers. The upper one is what people see and use: wallets, web pages, the programs that hold tokens or run an exchange, and the services that collect data about them. The lower one is what keeps the network alive: the validators that receive transactions, put them in blocks and agree on the result, and the software they run to do it.

A user only touches the upper layer, but every action there depends on the lower one. A program can be perfectly written and still be useless if the network cannot process its transactions, and a fast network has no value without applications that people want to use. Both layers need people who understand them well, and the work in each one is quite different.

02One transaction, both layers

Following a single transaction shows where one layer ends and the other begins. A web page builds the transaction and the wallet signs it. From that moment it leaves the application layer: an RPC node forwards it to the current leader, the leader runs the program and adds the result to a block, and the other validators vote on it until it is final. The page then receives the confirmation and shows the new state.

The application developer decides what goes inside the transaction. The people who work on consensus decide how fast and how safely it travels through the network.

03The consensus path

This path is about the network itself. The work includes operating validators and RPC nodes, studying how validators reach agreement, measuring performance and contributing to the clients, the programs a validator runs. Solana has more than one client, written by different teams, so that a bug in one of them does not stop the whole network:

  • Agave, maintained by Anza and written in Rust. It is the original client, and many validators run modified versions of it, such as Jito-Solana.
  • Firedancer, built by Jump Crypto from scratch in C. Its hybrid version, Frankendancer, combines Firedancer's networking and block production with Agave's execution and consensus, and the fully independent Firedancer is being adopted gradually.
  • Sig, built by Syndica in Zig and focused on reading data quickly. It is still in development.

The skills this path asks for are systems programming in Rust, C or Zig, Linux, networking and a good understanding of performance. Running a validator on mainnet also requires powerful hardware and SOL to pay for its votes, so most people start by watching the network from the command line and later practice on testnet, the network where validators test new versions.

A first step needs nothing but the Solana CLI. These commands ask the network about its current epoch and its validators:

bash
solana epoch-info
solana validators

The screen comes from a local test network with a single validator. Run the same commands with --url mainnet-beta and the list grows to hundreds of validators, each with its stake, its version and the client it runs.

04The applications path

This path is about what people do with the network. The work includes writing programs, building the clients and web pages that talk to them, connecting wallets, testing and collecting on-chain data so an app can show it quickly. Each part has its own tools:

  • Programs are written in Rust, usually with Anchor, or with lighter libraries such as Pinocchio when every compute unit counts.
  • Clients in TypeScript use @solana/kit, the official library for talking to the network, and tools like Codama can generate a client from a program's IDL.
  • Wallets announce themselves to web pages through the Wallet Standard, so one page works with Phantom, Solflare, Backpack and others without code for each one.
  • Tests run on simulated or local networks such as LiteSVM and Surfpool before anything reaches devnet.

The skills this path asks for are Rust for programs, TypeScript for clients and web pages, and a careful attitude to security, because a mistake in a program can lose other people's money.

A first step needs Node.js. Create a folder, install the library and save this script as balance.mjs:

bash
mkdir first-client && cd first-client
npm init -y
npm install @solana/kit
javascript · balance.mjs
import { createSolanaRpc, address } from "@solana/kit";

// Connect to devnet through its public RPC endpoint
const rpc = createSolanaRpc("https://api.devnet.solana.com");

// The wallet to read, passed on the command line
const wallet = address(process.argv[2]);

const { value: lamports } = await rpc.getBalance(wallet).send();
console.log("wallet: ", wallet);
console.log("balance:", Number(lamports) / 1_000_000_000, "SOL");

05How to choose

First stepexplore the network with the CLI, then testnetread data with @solana/kit, then write a program
You practice ona local validator and testneta local network and devnet

If you enjoy understanding how machines agree with each other and making systems faster, the consensus path will feel natural. If you prefer building something that people use, start with applications. The choice is not permanent, and the two paths meet often: application developers who understand the network write better programs, and core engineers who build applications understand what the network must deliver.

06Where to keep learning

Official documentation is the most reliable place to continue, because it is updated when the network changes.

Consensus

  • Anza docs: the Agave client, running a validator and the CLI.
  • Firedancer docs: Frankendancer and Firedancer for operators.
  • Sig docs: the Zig client and its goals.

Applications

  • Solana docs: core concepts, programs and clients.
  • Solana docs, frontend: @solana/kit and wallet connection.
  • Anchor docs: writing and testing programs.

This field manual ends here. You now know how the network is organized, how accounts, tokens, wallets and transactions work, and what it takes to write a program. Whichever path you take, the habit that will help most is the one used throughout these pages: run things yourself, read what the network answers and check every fact against the source.
