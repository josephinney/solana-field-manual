Writing safer programs

A Solana program is public. Anyone can call it, and the caller decides which accounts go into the transaction. Most security bugs in Solana programs come from trusting an account that nobody checked. This article takes a small Anchor program and shows which attack each of its checks stops.

  • levelbeginner
  • prerequisitesreading simple Anchor code
  • time~10 min
  • toolsAnchor 1.2.2

01Never trust the accounts you receive

Every Solana transaction lists the accounts its instructions will use, and it is the caller who writes that list. Your program cannot assume that the account called counter really is the right counter, or that the account called user really agreed to the call. It has to check, and each missing check is a door that someone can open.

The examples use a counter program written with Anchor. Each wallet has its own counter, stored in an account whose address is a PDA calculated from the word "counter" and the wallet's address. The initialize instruction creates the counter and increment adds one to it. These are the accounts that increment receives:

rust
#[derive(Accounts)]
pub struct Increment<'info> {
    pub user: Signer<'info>,
    #[account(
        mut,
        seeds = [b"counter", user.key().as_ref()],
        bump
    )]
    pub counter: Account<'info, Counter>,
}

It looks like a plain list of accounts, but almost every line is a security check. Anchor reads these declarations and writes the code that verifies them before your instruction runs. If any check fails, the transaction stops and nothing changes.

02Check who signed

Declaring user as a Signer means the transaction must carry that wallet's signature. To see why it matters, imagine the same struct written with UncheckedAccount, a type that accepts any account without checking anything:

rust · unsafe version, do not use
#[derive(Accounts)]
pub struct Increment<'info> {
    /// CHECK: nothing checks that this wallet signed
    pub user: UncheckedAccount<'info>,
    #[account(
        mut,
        seeds = [b"counter", user.key().as_ref()],
        bump
    )]
    pub counter: Account<'info, Counter>,
}

With this version, Bob could build a transaction that passes Ana's address as user, without her signature. The seeds would point to Ana's counter, so the check on the address would pass, and Bob would be changing Ana's counter. With Signer, the transaction is rejected, because only Ana can produce her signature.

Anchor makes this mistake hard to make by accident. Before it compiles a program with an UncheckedAccount, it asks for a comment starting with /// CHECK: that explains why the account is safe, and anchor build stops with an error if the comment is missing. When you write one, read it again and ask whether it is true.

03Check whose account it is

Declaring counter as Account<'info, Counter> adds two more checks. The first one is that the account must belong to this program, which means its owner must be the program's address. The second one is that its first 8 bytes must be the discriminator of Counter, the mark Anchor writes when it creates an account of that type.

Without these checks, someone could create an account with another program, fill it with any data they want and pass it as if it were a counter. In this program the seeds already fix the address, but many accounts are not PDAs, for example a settings account or a price feed. For those accounts, the owner and type checks are what keep a fake account out. If one of them fails, Anchor answers with AccountOwnedByWrongProgram or AccountDiscriminatorMismatch.

04Check that it is the right account

An account can belong to your program and be a real Counter, and still be the wrong one. Ana's counter and Bob's counter pass the checks of the previous section equally well. What tells them apart is the address, and that is what seeds and bump verify:

rust
seeds = [b"counter", user.key().as_ref()],
bump

Anchor calculates the PDA of "counter" and the address of the wallet that signed, and compares it with the account it received. If Bob signs and passes Ana's counter, the two addresses do not match:

A good habit is to write a test for this attack, so you know the check works and it keeps working when the code changes. This test creates a second wallet and tries to increment the first wallet's counter with it. It goes in the TypeScript test file, where program is the client for the program and counter is the first wallet's counter address:

typescript · tests/counter.ts
import { expect } from "chai";

it("does not let another wallet use this counter", async () => {
  // A second wallet that tries to increment this wallet's counter
  const other = anchor.web3.Keypair.generate();

  let failure: anchor.AnchorError | undefined;
  try {
    await program.methods
      .increment()
      .accountsPartial({ user: other.publicKey, counter })
      .signers([other])
      .rpc();
  } catch (err) {
    failure = err as anchor.AnchorError;
  }

  console.log("    error:     ", failure?.error.errorCode.code);
  console.log("    message:   ", failure?.error.errorMessage);
  expect(failure?.error.errorCode.code).to.equal("ConstraintSeeds");
});

The test passes when the transaction fails with the right error. ConstraintSeeds is the error Anchor returns when an account does not match its seeds:

[i] tests that must fail

It is natural to test that the program does what it should. It is just as important to test that it refuses what it should refuse: a missing signature, someone else's account, an amount that is too large. Attackers try exactly those cases.

05Be careful with numbers

A u64 can hold numbers up to about 18 quintillion. If a calculation goes past that limit it overflows, and a subtraction that goes below zero underflows. Without protection, the result wraps around: the maximum plus one becomes 0, and 0 minus one becomes the maximum. In a program that stores balances, that could turn a small balance into a huge one.

Anchor projects include a setting in Cargo.toml that turns these cases into errors:

toml · Cargo.toml
[profile.release]
overflow-checks = true

Keep it on. With it, count += 1 stops the transaction instead of wrapping around, but the error does not say what went wrong. You can make the intent visible with checked_add, which gives back None, Rust's way of saying there is no value, when the result does not fit. Then you turn that into an error with a clear name:

rust
pub fn increment(ctx: Context<Increment>) -> Result<()> {
    let counter = &mut ctx.accounts.counter;
    counter.count = counter.count.checked_add(1).ok_or(CounterError::Overflow)?;
    msg!("Counter is now {}", counter.count);
    Ok(())
}

#[error_code]
pub enum CounterError {
    #[msg("The counter reached its maximum value")]
    Overflow,
}

A counter will never reach the limit in practice, but the same pattern protects every calculation with balances, prices or fees. Use checked_sub for subtractions, checked_mul for multiplications and checked_div for divisions.

06Create each account only once

The initialize instruction creates the counter with init and sets count to 0. If someone calls it again for the same wallet, init fails because the account already exists, and the count is safe.

Anchor also offers init_if_needed, which creates the account only when it does not exist yet and otherwise uses the existing one. It is convenient, but in this program it would be a bug:

rust · initialize with init_if_needed, do not use here
#[account(
    init_if_needed,
    payer = user,
    space = 8 + Counter::INIT_SPACE,
    seeds = [b"counter", user.key().as_ref()],
    bump
)]
pub counter: Account<'info, Counter>,

With this version, a second call to initialize would not fail. It would run on the existing counter and set count back to 0. This is called a reinitialization bug, and in a program that stores who owns what, it can let someone overwrite data that was already there. That is why Anchor only accepts init_if_needed when you enable the init-if-needed feature in Cargo.toml. If you use it, make sure the instruction does not overwrite data when the account already exists.

07Know who can change your program

When you deploy a program, the wallet that deploys it becomes its upgrade authority, the only address that can replace its code later. Whoever controls that key controls the program, so it deserves the same care as a wallet with funds. You can see who it is with:

bash
solana program show <PROGRAM_ID>

Projects that handle real money usually move the upgrade authority to a multisig, an account that needs the signatures of several people to act. When a program is finished, it can also be made final, and from then on nobody can change or close it:

bash · irreversible
solana program set-upgrade-authority <PROGRAM_ID> --final
[!] --final cannot be undone

Once a program is final, there is no way to fix a bug in it. Only use it when you are sure the code is ready.

08Before you handle real money

The checks in this article cover the most common mistakes, but they are not a guarantee. Before a program holds funds that belong to other people, write tests for every case that should fail, ask other developers to review the code and have it checked by a professional audit, an independent review by a team that specializes in finding vulnerabilities. Even audited programs can have bugs, which is why some projects also limit how much money a new program can hold during its first weeks.

09Summary

In the codeWhat it stops
SignerActing for a wallet without its signature.
Account<'info, T>Accounts from another program, or with data of another type.
seeds, bumpPassing someone else's account of the right type.
overflow-checks, checked_addNumbers that wrap around past their limit.
initCreating an account twice and erasing its data.
/// CHECK:Forgetting why an unchecked account is safe.
upgrade authorityLosing control of who can change the code.

The rule behind all of them is the same. The caller chooses the accounts, so every account must prove it is the one your program expects before your code trusts it.
