Transactions and fees: reading the explorer

Every transaction on Solana is public, and an explorer shows all of it. In this file we open two real transactions from the same block, one that succeeded and one that failed, and learn to read them from top to bottom.

  • levelbeginner
  • prerequisitesnone
  • reading time~10 min

01What a transaction contains

A transaction is a signed message with four parts: the signatures of everyone who authorizes it, the list of accounts it will read or modify, the instructions that say which programs to run, and a recent blockhash that proves it was created recently. The first signer is the fee payer, the account that pays the network for processing it.

Once a validator includes the transaction in a block, an explorer can show you every one of those parts, plus what happened when it ran: the fee, the balances that changed and the messages each program wrote.

02Two real transactions

Both transactions in this file landed in the same block, slot 470,862,445, on 18 November 2026 at 08:08:21 UTC. You can open them yourself:

  • Successful: zv1tMRBf…QEcJT1k. Someone spent about 0.69 SOL to buy a token, routed through several exchanges.
  • Failed: Wv56GPKx…Sqrvbxx. A bot tried a chain of trades and cancelled them all.

Neither one is a simple transfer, and that is on purpose. Most transactions on mainnet are sent by apps and bots, so their pages list dozens of accounts and instructions. The trick is knowing that you only need to look at a few places, in this order: the summary, the fee, the balance changes, the instructions and, if something went wrong, the logs.

03The summary

The top of the page answers the basic questions: did it work, who paid, when it happened and how much it cost.

The signature doubles as the transaction's ID: it is what you search for and what appears in the address bar. Finalized means the block can no longer be reversed. The slot places the transaction in time, and the two fee lines are worth a section of their own.

04The fee

The fee has two parts. The base fee is fixed at 5,000 lamports for each signature, and this transaction had one. The priority fee is optional: the app offers to pay a price for each unit of work so that the leader picks the transaction sooner when the network is busy.

That work is measured in compute units (CU). Before sending, the app reserved a limit of 270,897 units and offered 0.01 lamports for each one, which gives the 2,709 lamports of priority fee. The transaction then used 231,289 units, but the priority fee is calculated on the units reserved, so a limit much larger than needed is money wasted.

The two parts also end up in different places: half of the base fee is burned, which removes it from the SOL supply, and the other half goes to the validator that produced the block, which also keeps the whole priority fee. In total, the transaction paid 0.000007709 SOL to the network.

05Balance changes

The account list shows every account the transaction touched, with the change in its SOL balance. Most of them show +0: they are programs, pools and token accounts whose SOL balance did not change. The useful rows are the ones that changed.

The fee payer lost 0.695180065 SOL, and the four non-zero rows add up exactly: 0.692034126 went to account 12, 0.00312823 to account 2, 0.00001 to account 4, and the remaining 0.000007709 is the network fee, which does not appear as a deposit anywhere. To see what was bought with that SOL, look at the token balances:

Account 12 is the SOL side of a trading pool, and in return the fee payer received 3,351,115 units of a token in its token account. That explains 0.692 of the 0.695 SOL. The two smaller transfers are something else: the app that built the transaction added them as separate instructions. The explorer cannot tell us why; apps often use transfers like these to collect their own fee or to tip validators for faster inclusion.

This is the most useful habit the explorer can teach you. Solana's network fee was a fraction of a cent, but the app took about 400 times more in its own transfer. When an operation seems expensive, the balance changes tell you exactly who charged what.

06Instructions and logs

The programs section lists the instructions in the order they ran:

Instructions #1 and #5 are the two SOL transfers you already found in the balances. #2 and #3 create token accounts with Create Idempotent, an instruction that creates the account if it does not exist and does nothing if it does, so the transaction works either way. #4 is the trade itself.

Programs can call other programs, and those calls appear as inner instructions, numbered #4.1, #4.2 and so on. Here the trade called a router, which called three exchanges, which in turn called the token programs to move the tokens: 18 inner instructions from a single line. An Unknown Program label only means the explorer has no name on file for that program, not that it is dangerous.

At the bottom of the page, the logs show what each program reported while it ran:

Each program writes when it starts, what it did, how many compute units it consumed and whether it succeeded. When everything works, you rarely need the logs. When something fails, they tell you where.

07When a transaction fails

The second transaction was sent by a bot that tried to profit from price differences between exchanges, in the same block as the first one.

The status says that instruction #2 failed, and the last line of the logs shows why: the bot's own program returned the error 0x1770. That code is 6000 in decimal, the number that programs written with the Anchor framework give to the first error they define. What it means depends on the program, and since this one is not public, we cannot know its exact reason, although bots like this one typically stop when a trade would not be profitable.

What we can see is more interesting: the logs show four trades that completed successfully before the error, yet every token balance changed by +0. That is because a transaction is atomic: either all of its instructions succeed, or none of their changes are kept.

The fee, however, is charged in both cases, because the validator did the work anyway: 250,299 compute units in this case. That is why the fee payer's balance went down by 0.000007828 SOL while nothing else changed.

08When a transaction expires

There is a third outcome that never reaches the explorer. The recent blockhash in every transaction is valid for 150 blocks, which with 200 ms slots is about 30 seconds. If the transaction has not been included in a block by then, validators discard it: nothing happens, no fee is charged, and the explorer has no page for it. Wallets usually detect this and offer to send it again with a new blockhash. The limit also protects you, since nobody can resend an old signed transaction weeks later.

Some transactions need more time than that, for example when several people have to sign them. For those cases, a transaction can use a durable nonce, a stored value that replaces the recent blockhash and does not expire. The failed transaction above uses one: its instruction #1, Advance Nonce, updates that stored value so the same signed transaction cannot be used twice.

09Summary

An explorer page looks overwhelming because it shows everything, but reading one is always the same routine:

  1. Status: did it succeed, and is it finalized?
  2. Fee: base fee plus priority fee, and how many compute units were used against the limit.
  3. Your balance changes: find your address, then check SOL and tokens. Every lamport has to go somewhere.
  4. Instructions: what programs ran, including transfers you did not expect.
  5. Logs: only if it failed, starting from the last line.
