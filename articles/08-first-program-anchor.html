Your first program with Anchor

In this hands-on guide you write a small Solana program, a counter that each user can increase, test it on your computer, deploy it to devnet and call it from the terminal. Every part of the code is explained, so you do not need to know Rust beforehand.

  • levelbeginner
  • prerequisitesa terminal on Linux, macOS or Windows with WSL
  • time~30 min
  • toolsAnchor 1.2.2, Solana CLI, Node.js
  • facts verified18 Nov 2026

01What we are going to build

The program has two instructions. initialize creates a counter for the user who calls it, starting at zero, and increment adds one to it. Each user gets their own counter, stored in an account whose address is a PDA calculated from the word "counter" and the user's wallet address. That way anyone can find a user's counter, and only that user can increase it.

We will use Anchor, the most widely used framework for writing Solana programs. It writes most of the repetitive code for you, especially the checks on the accounts each instruction receives, and it provides the commands to build, test and deploy.

02Install the tools

The Solana documentation offers a single command that installs everything you need: Rust, the Solana CLI, Anchor, Surfpool (a local Solana network for testing), Node.js and Yarn. On Windows, run it inside WSL.

bash
curl --proto '=https' --tlsv1.2 -sSfL https://solana-install.solana.workers.dev | bash

When it finishes, close the terminal, open a new one and check the versions:

bash
anchor --version
solana --version

This guide uses Anchor 1.2.2. If you see a different 1.x version, the steps should still work. If you have an older version such as 0.31 or 0.32, update it, because the project templates changed in 1.0.

You also need a wallet with some SOL on devnet. If you do not have one, create it and request test SOL:

bash
solana-keygen new
solana config set --url devnet
solana airdrop 2
[i] if the airdrop fails

The devnet faucet limits how many requests you can make. Use the web faucet at faucet.solana.com instead. You will need about 2 SOL for the deploy in section 07.

03Create the project

Anchor creates the whole project structure with one command:

bash
anchor init counter --template single --test-template mocha
cd counter

The two options are there to keep this first project simple. --template single puts the whole program in one file, which is easier to read from top to bottom. --test-template mocha writes the test in TypeScript, so the same file can test the program on your computer and later call it on devnet.

project tree
counter/
├── Anchor.toml              ← project settings: network, wallet, program ID
├── programs/
│   └── counter/
│       └── src/
│           └── lib.rs       ← the program, the file you will edit
├── tests/
│   └── counter.ts           ← the test, in TypeScript
├── target/
│   └── deploy/
│       └── counter-keypair.json   ← the keypair of the program's address
├── migrations/              ← optional scripts that run after a deploy
├── app/                     ← empty, for a future web app
├── Cargo.toml               ← Rust workspace
├── package.json             ← JavaScript dependencies for the test
├── rust-toolchain.toml      ← the Rust version for this project
├── security.json            ← contact details published with the program
└── tsconfig.json            ← TypeScript settings

Most of the time you will only touch two files: lib.rs, the program, and counter.ts, the test. The file counter-keypair.json deserves a mention too. It holds the keypair of your program's address, and Anchor uses it to deploy, so keep it as you would keep a wallet.

04The program, piece by piece

The project already comes with an example counter, but a slightly more complex one. Replace the whole content of programs/counter/src/lib.rs with this version:

rust · programs/counter/src/lib.rs
use anchor_lang::prelude::*;

declare_id!("2StLTr1uGxrDZfuwsASgfCY3toAVWwju6eWNsePBFsD5");

#[program]
pub mod counter {
    use super::*;

    pub fn initialize(ctx: Context<Initialize>) -> Result<()> {
        ctx.accounts.counter.count = 0;
        msg!("Counter created for {}", ctx.accounts.user.key());
        Ok(())
    }

    pub fn increment(ctx: Context<Increment>) -> Result<()> {
        ctx.accounts.counter.count += 1;
        msg!("Counter is now {}", ctx.accounts.counter.count);
        Ok(())
    }
}

#[derive(Accounts)]
pub struct Initialize<'info> {
    #[account(mut)]
    pub user: Signer<'info>,
    #[account(
        init,
        payer = user,
        space = 8 + Counter::INIT_SPACE,
        seeds = [b"counter", user.key().as_ref()],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub system_program: Program<'info, System>,
}

#[derive(Accounts)]
pub struct Increment<'info> {
    pub user: Signer<'info>,
    #[account(
        mut,
        seeds = [b"counter", user.key().as_ref()],
        bump
    )]
    pub counter: Account<'info, Counter>,
}

#[account]
#[derive(InitSpace)]
pub struct Counter {
    pub count: u64,
}
[!] keep your own program ID

Before replacing the file, copy the address inside declare_id! from the original, and paste it back into the new version. Every project gets a different one, so yours will not match the one shown here. If you lose it, run anchor keys sync, which writes the correct address back into the file.

Now let's go through it in five pieces.

1. The address

rust
use anchor_lang::prelude::*;

declare_id!("2StLTr1uGxrDZfuwsASgfCY3toAVWwju6eWNsePBFsD5");

The first line imports everything Anchor provides. declare_id! sets the program's address, the one stored in counter-keypair.json. Anchor uses it to check that the program is running at the address it expects.

2. The instructions

rust
#[program]
pub mod counter {
    use super::*;

    pub fn initialize(ctx: Context<Initialize>) -> Result<()> {
        ctx.accounts.counter.count = 0;
        msg!("Counter created for {}", ctx.accounts.user.key());
        Ok(())
    }

    pub fn increment(ctx: Context<Increment>) -> Result<()> {
        ctx.accounts.counter.count += 1;
        msg!("Counter is now {}", ctx.accounts.counter.count);
        Ok(())
    }
}

The module marked with #[program] contains the instructions, and each pub fn becomes one that anyone can call. Both receive a ctx, the context, which holds the accounts the instruction works with, and both return Ok(()) when everything went well. msg! writes a line in the transaction logs, the same logs an explorer shows.

Notice how little the instructions do: one sets the number to zero and the other adds one. All the work of creating the account and checking that it is the right one happens in the next two pieces.

3. The accounts for initialize

rust
#[derive(Accounts)]
pub struct Initialize<'info> {
    #[account(mut)]
    pub user: Signer<'info>,
    #[account(
        init,
        payer = user,
        space = 8 + Counter::INIT_SPACE,
        seeds = [b"counter", user.key().as_ref()],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub system_program: Program<'info, System>,
}

A struct marked with #[derive(Accounts)] lists the accounts an instruction needs, and the attributes on each one tell Anchor what to check before running any code:

  • user is a Signer: the transaction must be signed by this wallet. It is marked mut because its balance changes when it pays for the new account.
  • counter is created by init, paid for by the user (payer = user), with room for space bytes, at the PDA calculated from seeds. bump asks Anchor to find the bump that makes the address valid.
  • system_program is required because creating an account is a job for the System Program, which Anchor calls for you.

4. The accounts for increment

rust
#[derive(Accounts)]
pub struct Increment<'info> {
    pub user: Signer<'info>,
    #[account(
        mut,
        seeds = [b"counter", user.key().as_ref()],
        bump
    )]
    pub counter: Account<'info, Counter>,
}

Here counter is not created but modified, so it is marked mut. The seeds include the address of the signer, which is what guarantees that each user can only increase their own counter. If someone passes another person's counter, Anchor calculates the PDA from the signer's address, sees that it does not match and rejects the transaction before increment runs.

5. The data

rust
#[account]
#[derive(InitSpace)]
pub struct Counter {
    pub count: u64,
}

#[account] defines what a counter account stores: a single number, count, of type u64, an unsigned integer of 8 bytes. InitSpace calculates that size for you, and that is where the space in piece 3 comes from:

The first 8 bytes are the discriminator, a fixed value Anchor writes at the start of every account it creates so it can tell what kind of data an account holds. That is why space is always 8 + the size of your data.

05The test

Replace the content of tests/counter.ts with this:

typescript · tests/counter.ts
import * as anchor from "@anchor-lang/core";
import { Program } from "@anchor-lang/core";
import { Counter } from "../target/types/counter";

describe("counter", () => {
  const provider = anchor.AnchorProvider.env();
  anchor.setProvider(provider);
  const program = anchor.workspace.counter as Program<Counter>;

  // The address of this wallet's counter: the PDA of ["counter", wallet]
  const [counter] = anchor.web3.PublicKey.findProgramAddressSync(
    [Buffer.from("counter"), provider.wallet.publicKey.toBuffer()],
    program.programId
  );

  it("creates and increments the counter", async () => {
    // Create the counter only the first time
    const existing = await program.account.counter.fetchNullable(counter);
    if (!existing) {
      const tx = await program.methods.initialize().accountsPartial({ counter }).rpc();
      console.log("    initialize:", tx);
    }

    const tx = await program.methods.increment().accountsPartial({ counter }).rpc();
    console.log("    increment: ", tx);

    const account = await program.account.counter.fetch(counter);
    console.log("    counter:   ", counter.toBase58());
    console.log("    count:     ", account.count.toString());
  });
});

Reading from the top:

  • AnchorProvider.env() loads the network and the wallet from Anchor.toml and the command line, so the same test runs on your computer or on devnet.
  • anchor.workspace.counter gives you a client for the program, generated from its IDL, a description of its instructions and accounts that Anchor creates when it builds.
  • findProgramAddressSync calculates the counter's PDA with the same seeds as the program.
  • The test creates the counter only if it does not exist yet, increases it and prints the count. You do not need to pass user: Anchor fills in signer accounts with your wallet.

06Build and test on your computer

Build the program and run the test:

bash
anchor build
anchor test

anchor build compiles the program into target/deploy/counter.so and generates its IDL. anchor test then starts a local network, deploys the program on it, runs the test and shuts the network down. The first build takes a few minutes, because it downloads and compiles the dependencies.

[i] about these screens

The screens in this guide show example output, with the format Anchor 1.2.2 uses. Your addresses, signatures and times will be different, and Anchor may print a few extra lines while it builds and starts the network.

07Deploy to devnet

Deploying copies the compiled program to the network, where it stays in an account at your program's address. That account needs a refundable deposit proportional to the size of the program, so make sure you have at least 2 SOL on devnet:

bash
solana balance
anchor deploy --provider.cluster devnet

Program ID is your program's address on devnet. The upgrade authority is your wallet, so you can deploy new versions of the code to the same address later. Anchor also publishes the IDL, which lets explorers and other apps read your program's accounts.

08Call it on devnet

The test you wrote is also a way to call the program. Run it against devnet, telling Anchor to skip the build, the deploy and the local network:

bash
anchor test --skip-build --skip-deploy --skip-local-validator --provider.cluster devnet

Run the same command a second time:

The first run creates your counter and leaves it at 1. The second finds it already there, skips initialize and leaves it at 2. Each run sends real transactions to devnet, and the counter keeps its value between them, because it lives in an account on the network, not on your computer.

09See it in the explorer

Open your program and your counter in the explorer, replacing the addresses with the ones from your output:

bash
https://explorer.solana.com/address/<PROGRAM_ID>?cluster=devnet
https://explorer.solana.com/address/<COUNTER_ADDRESS>?cluster=devnet

The program's page shows it as an executable account with your wallet as upgrade authority, and lists every transaction that called it. On the counter's page you will see that its owner is your program and that it holds 16 bytes of data. Explorers that read the IDL Anchor published can also show the count already decoded.

10Clean up

When you no longer need the program, you can close it and recover the deposit:

bash
solana program close <PROGRAM_ID> --bypass-warning
[!] closing is permanent

A closed program cannot be deployed again at the same address. On devnet that only means using a new address for your next deploy, but on mainnet it is irreversible.

11Summary

You wrote a program with two instructions, defined which accounts each one needs and what Anchor must check, stored each user's data in a PDA, tested everything on your computer and used the same test to call the program on devnet.

anchor buildCompiles the program and generates its IDL.
