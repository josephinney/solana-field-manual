Programs: how smart contracts work on Solana

A program is code that lives on the network and runs on every validator. On Solana that code keeps no data of its own, and this one design decision explains how programs store information, how they call each other and why the network can run so many of them at once.

  • prerequisitesnone
  • reading time~9 min
  • facts verified18 Nov 2026

01What a program is

A program, which other blockchains call a smart contract, is compiled code stored in an account. Developers usually write it in Rust and compile it to a compact bytecode that every validator can run in an isolated environment, so the same instruction produces exactly the same result on every machine.

The account that holds the code is marked as executable, and its address is the program's ID, which is how transactions say which program they want to run. Most programs are deployed with an upgrade authority, an address that can replace the code with a new version. When that authority is removed, the program can never change again, which is why some projects remove it once their code is final.

02Code in one place, data in another

On Solana, a program does not store any data inside its own account. All the information it works with, such as balances, settings or user records, lives in separate data accounts whose owner is the program.

Take a simple counter that each user can increase. The program account holds only the code that adds one to a number, and every user's number lives in an account of its own:

The network enforces a few rules on every account, and they are what keeps this arrangement safe:

  • Only the owner program can change an account's data or take lamports out of it.
  • Anyone can add lamports to an account.
  • An account can hold up to 10 MiB of data, and it must keep a refundable SOL deposit proportional to its size.

When a transaction calls a program, it passes the list of accounts the program will use, and the program receives them as inputs. A well-written program checks each of them before trusting it: that the account belongs to the right owner, that the expected person signed, and that the address is the one it should be. Skipping those checks is one of the most common sources of bugs in Solana programs.

03Accounts that belong to a program: PDAs

If every user's counter lives in a separate account, two questions follow: how does anyone find Ana's counter, and who controls an account that belongs to a program rather than to a person? Both have the same answer, the Program Derived Address, or PDA.

A PDA is an address calculated from a few values chosen by the program, called seeds, plus the program's own address. For Ana's counter, the seeds could be the word "counter" and Ana's address. The network hashes them with SHA-256 together with one extra number, the bump, starting at 255. If the result happens to be a valid public key, one that could have a private key, it tries again with 254, then 253, and keeps the first one that is not.

Those are real values for an example program: with bumps 255 and 254 the result could have had a private key, so both were rejected, and 253 produced the address. Because nobody can hold a private key for it, the only one that can authorize changes to a PDA is the program whose address went into the calculation. And because the inputs are public, anyone can repeat the calculation and find Ana's counter without asking anyone.

In Anchor, the most common framework for writing programs, the seeds are declared next to the account:

rust · anchor
// The data each counter account stores
#[account]
pub struct Counter {
    pub count: u64,
}

// The accounts the increment instruction receives
#[derive(Accounts)]
pub struct Increment<'info> {
    // Ana's counter: the PDA of ["counter", Ana's address]
    #[account(mut, seeds = [b"counter", user.key().as_ref()], bump)]
    pub counter: Account<'info, Counter>,
    pub user: Signer<'info>,
}

// The instruction itself, inside the program module
pub fn increment(ctx: Context<Increment>) -> Result<()> {
    ctx.accounts.counter.count += 1;
    Ok(())
}

Before running increment, Anchor recalculates the PDA from the seeds and checks that the account it received is exactly that one, which is the kind of account check described in section 02.

PDAs you have already met

Associated token accounts are PDAs too. They belong to the Associated Token Program, and their seeds are the wallet address, the token program and the token's mint. With those three values, the USDC account of Ana's wallet 7xKX…sAsU is always 2yF5…dkjZ, so any app can send her USDC without asking where to put it. Many programs also use PDAs as vaults: accounts that hold tokens on behalf of the program, which only its code can move.

04Programs that call other programs

A program can call another program in the middle of its own execution, which is known as a cross-program invocation or CPI. This is how programs reuse each other instead of reimplementing everything: an exchange does not move tokens itself, it asks the Token Program to do it.

In a swap, the program makes two calls. To take Ana's tokens, it calls the Token Program and passes along Ana's signature, because the signature of the transaction remains valid in the calls it triggers. To pay her back from the pool, it calls the Token Program again, but the pool's tokens sit in a vault that is a PDA, and nobody has its private key. In that case the swap program signs for the PDA itself by providing the seeds, something only the program that derived it is allowed to do.

Each of these calls appears in an explorer as an inner instruction. On mainnet, a chain of calls can be at most 4 levels deep. An upgrade that raises the limit to 8 has been approved and already runs on local test validators, but it is not active on mainnet yet. One restriction does not change: a program cannot be called again through another program it called, so A → B → A is never allowed.

05Why this design runs in parallel

Every transaction declares in advance every account it will read or write. With that list, the validator can see before running anything which transactions touch the same accounts, and send the ones that do not to different CPU cores at the same time.

This is where keeping code and data apart pays off. Because the counter program holds no data of its own, a thousand users can call it in the same block without waiting for each other, as long as each one writes to their own counter. If the program had stored every count in a single shared account, every transaction would write to that account, and they would have to run one after another.

Popular accounts, such as the pool of a busy trading pair, still create queues, since everyone who trades in it writes to it. That is why well-designed programs give each user their own account wherever they can.

06Summary

A Solana program is code without data. Its state lives in accounts the program owns, often at addresses derived from seeds so that anyone can find them and only the program can control them. Programs call each other to reuse functionality, and because every transaction declares its accounts in advance, the ones that touch different accounts run in parallel.
